# Zotero MCP Integration

The preferred connector is [`cookjohn/zotero-mcp`](https://github.com/cookjohn/zotero-mcp), a Zotero plugin with an integrated Streamable HTTP MCP server. Its README documents collection browsing, item lookup, content extraction, full-text database access, and identifier-based import with optional attachment retrieval. Tool names and schemas can change; the executor must inspect the active MCP tool definitions rather than assume a particular version.

## Connection

The documented setup uses Zotero 7+, installs the plugin release from the repository, enables its server in Zotero preferences, and connects the MCP client using the configuration generated by the plugin. The README documents `http://127.0.0.1:23120/mcp` as the default endpoint. The project workflow uses an already-configured MCP connector; it does not edit a user's client configuration or install software.

For a standalone Python client, install the optional extra on Python 3.10 or
newer and check the active endpoint:

```powershell
python -m pip install -e ".[mcp]"
sci-nma-agent zotero-mcp-check --url http://127.0.0.1:23120/mcp
```

The check initializes the MCP session and lists its current tool names,
descriptions, and schemas. It does not read or write Zotero library records.
The library exposes `ZoteroMCPReadClient` for a workflow executor that needs to
resolve a collection, page through items, inspect a record, or request cached
content. Tool discovery is refreshed at connection time; only advertised
read capabilities with a conservative name/schema allowlist are callable
through that facade. An MCP `readOnlyHint` is retained when supplied; a false
hint blocks the tool, while absence of this optional annotation is not treated
as proof of mutability. Mutating names, parameters, and action choices remain
blocked. If no MCP server is running, keep the connection error in the retrieval
audit and use the local read-only bridge when available.

To persist one collection's MCP evidence and extracted text without modifying
Zotero:

```powershell
sci-nma-agent zotero-mcp-export --project PROJECT --collection COLLECTION_NAME --match-by name --page-size 100
```

The export writes `original_materials/zotero_mcp/manifest.json` and
`original_materials/zotero_mcp/corpus.jsonl`. It retains collection-resolution
evidence, every item page and its arguments, per-item detail/content responses,
retrieval status, canonical raw-response hashes, extracted-text hashes, and
page locators only when the server explicitly returns them. Pagination follows
server totals, `hasMore`, cursors, or advancing offsets; a repeated page or an
unverifiable continuation is reported as incomplete. Multiple attachments or
missing attachment identities are marked ambiguous and are not selected.

This MCP export is a raw retrieval corpus, not the gated
`full_text_retrieval_manifest.json`: it does not create study/report IDs, join
to approved screening records, establish eligibility, or mark a fact absent.
The stage executor must perform that crosswalk and manual confirmation in the
subsequent gated workflow. Tests use mocked MCP sessions; no live endpoint or
Zotero library schema was verified for this implementation. Tool names and
schemas are inspected from each connected server at runtime.

## Capability Boundary

| Workflow action | Where it happens | Current integration behavior |
|---|---|---|
| Create the project collection, import citations, and let Zotero fetch attachments | Zotero desktop/plugin, performed by the user | Outside this CLI; the MCP facade never invokes library writes or downloads |
| Resolve and enumerate the named collection | Zotero MCP server | `zotero-mcp-export` uses only advertised, schema-matched read capabilities |
| Extract cached text and check full-text state | Zotero MCP server, when a compatible read schema is advertised | Export preserves the exact call, attachment identity, returned locators, and hashes |
| Confirm a manually attached report and resume retrieval | `manual-fulltext confirm` plus the gated review workflow | Re-reads the exact item/attachment, records provenance, versions the manifest, and reopens retrieval; raw export alone does not confirm a report |

Upstream plugin versions may expose `add_by_identifier`, attachment-download,
or tag-writing tools. This adapter does not call those operations. Do not treat
their presence in an upstream README as an implemented CLI capability. Import
reports into the project collection and trigger Zotero's own attachment
retrieval in the desktop application; the agent reads the resulting collection.

## Retrieval and Fact States

Record `retrieval_status`, `full_text_review_status`, and `fact_status`
separately. A connector returning a parent item is not proof that its PDF is
attached; a text-extraction result is not proof that the full report has been
reviewed. If attachment selection or item identity is ambiguous, queue it for
manual resolution instead of choosing the first match.

If automated retrieval yields no usable report, create one manual queue row
per report with the tried routes, missing identifier/attachment details, and
next action. Routes include Zotero retrieval, DOI/PMID open-access repository
search, institutional library access, interlibrary loan, and corresponding-
author contact. Notify the user with the queue, then pause only dependent work.
The retrieval-stage submit gate creates and hash-binds
`screening/retrieval_attempts/run-NNNN/manual_fulltext_queue.json` when the
manifest contains unresolved or manually confirmed rows. To build or display
the current report-level handoff while the retrieval attempt is in progress:

```powershell
sci-nma-agent manual-fulltext queue --project PROJECT `
  --manifest screening/full_text_retrieval_manifest.json `
  --study-report-map corpus/study_report_map.json `
  --screening-manifest screening/title_abstract_screening_manifest.json
```

The command prints each queued report, its unresolved reason, acquisition
routes, and next actions. After obtaining a candidate, attach it to the exact
parent item in Zotero and explicitly confirm it against the queue:

```powershell
sci-nma-agent manual-fulltext confirm --project PROJECT `
  --manifest screening/retrieval_attempts/run-0001/full_text_retrieval_manifest.json `
  --queue screening/retrieval_attempts/run-0001/manual_fulltext_queue.json `
  --study-report-map corpus/study_report_map.json `
  --screening-manifest screening/title_abstract_screening_manifest.json `
  --study-id STUDY_ID --report-id REPORT_ID `
  --item-key ZOTERO_ITEM_KEY --attachment-key ZOTERO_ATTACHMENT_KEY `
  --attachment-file PATH_TO_ATTACHED_PDF --actor USER_ID `
  --identity-evidence "Matched the screened citation to the Zotero record" `
  --agent retrieval-agent --agent-session SESSION_ID
```

Confirmation re-reads the exact parent item and requests complete content with
the selected attachment key through MCP. It compares item metadata with the
approved report identity and retains both raw responses, their hashes, exact
tool arguments, and the text returned for that attachment. That MCP-returned
text is the attachment-bound source for downstream review. The file supplied
to `--attachment-file` is archived separately as a
`unverified_user_supplied` local copy: its basename is checked against Zotero
metadata, but its bytes are not represented as cryptographically identical to
the Zotero attachment. Use the read-only `zotero-fulltext --source` bridge when
local Zotero storage is available and exact stored-file provenance is required.

Confirmation writes a new versioned retrieval manifest, queue, text artifact,
and local-copy artifact, then resumes or hands off the retrieval stage. The
executor must submit the new manifest and queue; two fresh independent reviews
are required before dependent stages are released. Prior artifacts and review
reports remain archived by the ledger. A uniquely matched automatic retrieval
does not require manual confirmation.

Before retrieval and confirmation, use `not_assessed_pending_full_text`.
After retrieval but before independent review and adjudication, use
`pending_full_text_review`. A completed, adjudicated report review may establish
`not_reported_in_reviewed_report` only with documented section/page coverage.
Study-level `not_reported_after_all_linked_sources_review` requires coverage for
every report in the approved study/report map; the extraction manifest is
hash-bound to the map, retrieval manifest, and full-text eligibility manifest
and checked against their approved report states by the stage ledger. Use
`cannot_tell_after_full_text_review` when the retrieved, adjudicated sources do
not resolve whether the fact was reported. These missingness states do not mean
an outcome was unmeasured or a numeric value was zero. Failed retrieval,
inaccessible content, OCR failure, ambiguous identity, or an absent attachment
never establishes factual absence.

If no Zotero MCP connection is exposed in the current agent runtime, report
that connection state and use the existing read-only local Zotero bridge as a
fallback. Never claim an MCP call succeeded when it was not available.

Tool names and endpoint details above reflect the workflow's recorded Zotero
MCP documentation as of 2026-09-25. The upstream repository and a live Zotero
endpoint were not independently inspected during this implementation. The
connected server's runtime `list_tools` schemas are authoritative for each
execution; run `zotero-mcp-check` before exporting a collection.
